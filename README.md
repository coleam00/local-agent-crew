# A local agent crew that works through GitHub issues around the clock

**The question:** how much would my daily token usage cost through a cloud API, versus running it all locally?

I pointed a crew of four local AI agents at the GitHub issues of [Archon](https://github.com/coleam00/Archon), my open
source AI coding harness, and ran them on an [ASUS ProArt P16](https://www.asus.com/laptops/for-creators/proart/proart-p16-h7607/)
with 128GB of unified memory. Each agent triages an issue, finds the root cause, posts what it found, and opens a PR
with tests when the fix is simple. Harder issues get a root-cause write-up and are labelled for cloud planning. I
review every PR before anything merges.

The crew works in [dynamous-business/local-agent-crew-archon](https://github.com/dynamous-business/local-agent-crew-archon),
a standalone copy of Archon, so it never touches the real repo. Every issue comment and PR it made is there.

## How it works

```
Archon issues ──mirror──▶ crew repo (crew:queued)
                               │
               dispatcher keeps 4 agents busy, one Archon run per issue, each in its own worktree
                               │
   triage (read-only) ─▶ root cause posted on the issue ─┬─▶ simple fix: implement ─▶ type-check + tests ─▶ review ─▶ PR
                                                         └─▶ harder: labelled needs-cloud-planning
```

| File | What it does |
|---|---|
| `crew/local-crew-issue.yaml` | The Archon workflow. The fix loop only ends when the real checks print `VALIDATION: PASS` and the review is clean, so the model can't talk its way past a failing test |
| `crew/mirror_issues.py` | Copies new Archon issues into the crew repo with @mentions and issue references defused, so the experiment never pings anyone |
| `crew/sync_fork.sh` | Keeps the crew repo's `dev` branch level with Archon's, hourly |
| `crew/dispatcher.py` | Keeps N agents busy and records every run in `data/runs.jsonl` |
| `crew/telemetry.py` | Every 10 s: GPU power, GPU memory and llama-server's token counters into `data/telemetry.csv` |
| `crew/dashboard.py` | The live dashboard (`/`) and the agents page (`/agents`) from the video |
| `crew/results.py` | Computes every number above |
| `crew/calibrate_power.py`, `crew/bench.py`, `crew/broll_session.py` | Power calibration, throughput benchmark, and the no-post agent sessions used for screen recording (excluded from the results) |

## How the numbers are measured

- **Issues worked:** distinct Archon issues, each counted once at its latest attempt. For the first-day table, an issue counts if that attempt finished inside the 24 hours. Runs that failed for infrastructure reasons and were re-queued are not counted as results.
- **Tokens:** llama-server's own counters (`/metrics`). Input counts both freshly processed and cache-served prompt tokens.
- **Cloud cost:** the same model on a cloud API (`qwen/qwen3.8-flash` on OpenRouter) at the list price recorded in `data/cloud_prices.json`, with cached input at the cached rate.
- **Electricity:** whole-laptop power, calibrated on battery against the GPU power reading (`data/power.json` has the fit), integrated over the window at Minnesota's average residential rate (16.9 cents/kWh, EIA, May 2026).
- **Excluded:** the calibration load and every screen-recording session, listed with reasons in `data/power.json` (`exclude_windows`).

## What worked and what didn't

I audited the first 24 PRs the crew opened: checked out each one, ran its tests, then reverted the fix and ran them again.

- **20 of 24 PRs were good.** In 20 of the 21 PRs with a code fix, the new tests pass with the fix and fail without it. No deleted tests, skips or loosened assertions.
- **3 need work and 1 is a duplicate.** One test passes even without its fix, one PR missed an old test that still asserts the removed behaviour, one is a test change for an issue the maintainers had parked, and one duplicates another PR.
- **Triage was accurate:** 14 of 15 sampled root-cause write-ups were right, with about 132 of 136 file:line references correct.
- **Most issues need a person or a bigger model to plan.** 115 of the 176 first-day issues were labelled `needs-cloud-planning`. The crew is best at finding root causes and fixing the small things.
- **A process bug to fix:** several PR branch names and commit trailers point at the wrong issue number (the PR body's `Fixes #N` is right).

## Reproduce it

1. Download llama.cpp's `win-cuda-13.5-arm64` build and the model: `unsloth/Qwen3.8-Flash-Next-GGUF` (`UD-IQ4_XS/`) plus `ggml-org/Qwen3.8-Flash-Next-GGUF` (`mtp-Qwen3.8-Flash-Next-Q8_0.gguf`).
2. Make your own copy of the repo you want worked (a fork or a standalone copy), enable issues, clone it and `bun install`. Put `crew/local-crew-issue.yaml` in `.archon/workflows/local-crew/`.
3. Register the local server with Pi (`crew/pi-models.json` goes to `~/.pi/agent/models.json`) and use `crew/archon-config.yaml` as `~/.archon/config.yaml`.
4. Set the repo name in `crew/mirror_issues.py` and the paths at the top of `crew/start_crew.ps1`, then run `powershell -File crew/start_crew.ps1 -Agents 4`. It starts the model server, telemetry, dashboard, mirror, sync and dispatcher.
5. `python crew/results.py --md` at any time for the numbers.
